# R2 and presigned URLs

What was run and what was not. "This repository" means this code; "the prototype" is the private project this design
comes from, which ran the same ideas with its own code on Cloudflare `standard-4` on 2026-11-28.

| Part | This repository | The prototype |
| --- | --- | --- |
| No R2: chunks between instances, output streamed from an instance | tested on Cloudflare (version 0.1.0) | tested; this is where transfers arrived damaged ([failures.md](failures.md)) |
| R2 through the Worker's binding (gateway): chunks up, chunks down, output up, download, delete | tested on Cloudflare with version 0.1.0 (Remotion and mixed examples, 2 and 4 instances). The per-run keys, the SHA-256 on uploads and the checked downloads of this version ran against a store in memory only | tested; slower than direct: 0.53 MB/s up from a laptop, 85.0 s for a 3.9 GB output |
| Multipart upload of large outputs through the gateway | ran on Cloudflare only with its threshold lowered to 8 MiB (a 29 MB file, hash verified after download). No output above 100 MiB was produced | |
| **Presigned direct transfer**: client to R2, container to R2, R2 to client, bytes never through a Worker | **not run on R2.** The presigner is unit-tested against a known SigV4 implementation; a whole render over presigned URLs ran against an S3 stand-in in memory (`packages/core/test/e2e-storage.ts`). Without keys the service answers `501`; that answer was tested on Cloudflare | **verified for real.** Presigned PUT 200, GET 200 with the right body, DELETE 204. A one-hour 1080p job went through it end to end: 1,200 chunk objects up and down with 0 checksum mismatches, a 3.91 GB output uploaded from the joining instance in 59 parts in 40.9 s, downloaded at 5.6 MB/s with the SHA-256 equal to the one computed where the file was made |
| Presigned download URL of the output (`?presign=`) | **not run on R2** (same presigner) | part of the row above |
| Client-side multipart upload of inputs, resumable | unit-tested against the S3 stand-in ([inputs.md](inputs.md)) | built and unit-tested; no input above 90 MB went through R2 in the measured runs |

## Without R2 (tested)

Nothing to set up.

- A chunk travels from the instance that rendered it to the instance that joins: container, then the coordinator
  (a Durable Object), then container. Each file's SHA-256 is compared on arrival; a damaged transfer is repeated.
- The finished file stays on the joining instance. `GET /renders/<id>/output` streams it through the Worker. The
  client checks the hash again.
- Delete the render when you have the file (`DELETE /renders/<id>`, the CLI does it). Until then one instance stays
  up. If it goes away first (inactivity timeout, 15 minutes after the render, a host restart) the output is gone and
  the answer is `410`.

This is fine for your own renders, fetched right away. It is the wrong shape for files that must stay available.

Limits to know: the body of a request from a Durable Object to a container counts against a 100 MiB default limit
on outbound request bodies, so a single chunk must stay under 100 MiB. At 10 Mbit/s that is 80 seconds of video.
The final file is a response body, which has no enforced size limit.

## With R2 (tested)

1. Create a bucket and bind it in the example's `wrangler.jsonc`:

   ```jsonc
   "r2_buckets": [{ "binding": "RENDER_BUCKET", "bucket_name": "my-renders" }]
   ```

   ```bash
   npx wrangler r2 bucket create my-renders
   ```

2. Deploy. `GET /health` now says `"storage": true`.

What changes:

- Each render instance uploads its own chunks. Every run of a chunk has its own keys:
  `renders/<renderId>/chunk-0003-r1.ts`, and `chunk-0003-r2.ts` for a retry or a hedge. A run that finishes late can
  never overwrite the run that won; that happened in the prototype when two runs wrote the same key
  ([failures.md](failures.md#one-run-one-set-of-files)). The joining instance is told which runs won, downloads
  those and uploads `renders/<renderId>/output-s0-0`. No file passes through the coordinator.
- Every transfer is checked. An upload carries the file's SHA-256 and R2 refuses a body that does not match. The
  joining instance compares each chunk with the size and SHA-256 recorded where it was rendered before it joins a
  byte of it.
- The containers hold **no R2 credentials**. They make plain HTTP requests to `http://r2.internal/<key>`. The
  Durable Object registers an outbound intercept for that host when it starts the container
  (`ctx.container.interceptOutboundHttp`), and the `R2Gateway` entrypoint in the Worker answers from the R2 binding.
  The gateway only serves keys under the render's own prefix, so one render cannot read another's files.
  Source: https://developers.cloudflare.com/containers/configuration/workers-connections/
- Requests through an intercept are limited to 100 MiB too (Cloudflare's limits page). Outputs above 90 MiB are
  uploaded in 64 MiB parts (R2 multipart upload through the same gateway). `RENDER_MULTIPART_ABOVE_MIB` in
  `CONTAINER_ENV` lowers the threshold, which is how we tested it.
- `GET /renders/<id>/output` streams from R2. Every instance is stopped as soon as the render is done: after our
  R2 renders the progress showed 0 instances.
- `DELETE /renders/<id>` deletes the objects, also those of runs that lost. Add an R2 lifecycle rule if you would
  rather have them expire.

## Direct transfer over presigned URLs (not run on R2 by us)

Through the gateway every byte passes a Worker. That is simple and needs no keys, and it is the slower road: in the
prototype a laptop uploaded at 0.53 MB/s through the Worker and at 8.7 MB/s straight to R2, and the joining instance
needed 85.0 s through the Worker and 40.9 s direct for the same 3.9 GB output.

With `R2_DIRECT` the coordinator signs one URL per object a task reads or writes, and puts the URLs into the task.
The containers still hold **no keys**: a URL is good for one method on one key for a limited time.

1. Give the service R2 S3 API keys and the bucket's coordinates (the same four values as for presigned downloads,
   below), and set:

   ```jsonc
   "vars": { "R2_DIRECT": "true", "R2_ACCOUNT_ID": "<your account id>", "R2_BUCKET_NAME": "my-renders" }
   ```

2. Keep the bucket binding: the Worker still reads the output and deletes through it.

What changes: the containers PUT and GET at `https://<account id>.r2.cloudflarestorage.com/...`, so
`ENABLE_INTERNET` must stay `"true"`. Each upload is one PUT, checked by its ETag (for S3 and R2 the ETag of a single
PUT is the MD5 of the body). One PUT carries about 5 GB at most. The streamed fragmented MP4 of
[long-videos.md](long-videos.md) is not available in this mode: it uses the gateway's multipart calls.

The code is `packages/core/src/s3-presign.ts` (SigV4 query signing with WebCrypto, so it runs in a Worker and in
Node). It derives the signing key once a day and then needs two HMACs per URL; a long job signs thousands.

### Sign as little as possible

An R2 API token is usually wider than one render: every key of the bucket, sometimes more buckets. So do not sign
whatever a caller asks for. `packages/core/src/signer.ts` is the policy the prototype put in front of its presigner,
for a service with several users:

| Rule | Why |
| --- | --- |
| One bucket, fixed where the presigner is made. No call takes a bucket name | a key that reaches other buckets cannot be pointed at them |
| Inputs only under `inputs/<user>/<sha256>` | content-addressed: the same file is uploaded once; a user cannot name another user's prefix |
| Everything of a job under `jobs/<user>/<job>/` | one job cannot read or overwrite another's chunks or output |
| Only GET, PUT, HEAD and the multipart calls; DELETE and listing only for a cleanup scope, and never on inputs | a leaked task cannot delete or enumerate |
| At most 6 hours | long enough for a long join, short enough to expire |
| The service's own storage calls pass the same check | a bug elsewhere cannot touch another user's objects either |

`refusal(scope, request)` returns `null` or the reason. There are unit tests for the keys it must refuse: another
user, another job, `..`, a listing of a whole prefix, a query on a plain object, an expiry over 6 hours.

This repository's own service has one tenant and one secret, and its coordinator only ever asks for keys under
`renders/<its own render id>/`. It uses the presigner without the multi-user policy. If you put users in front of
it, put the policy in too.

## Presigned download URLs (not run on R2 by us)

A presigned URL lets someone download the file without your secret, for a limited time. The R2 binding cannot make
one: "The R2 Workers API binding cannot generate presigned URLs"
(https://developers.cloudflare.com/r2/api/s3/presigned-urls/). It needs R2's S3 API keys.

1. Create an R2 API token with read access to the bucket (dashboard, R2, "Manage API tokens").
2. Give the service the keys as secrets, and two plain variables:

   ```bash
   npx wrangler secret put R2_ACCESS_KEY_ID
   npx wrangler secret put R2_SECRET_ACCESS_KEY
   ```

   ```jsonc
   "vars": { "R2_ACCOUNT_ID": "<your account id>", "R2_BUCKET_NAME": "my-renders" }
   ```

3. Ask for a URL:

   ```bash
   curl -H "Authorization: Bearer $RENDER_SECRET" "$RENDER_SERVICE_URL/renders/<id>/output?presign=3600"
   # {"url":"https://<account>.r2.cloudflarestorage.com/my-renders/renders/<id>/output?X-Amz-..."}
   ```

   or `presignUrl({ renderId, expiresInSeconds: 3600 })`.

Facts from the R2 docs: expiry is 1 second to 7 days. Presigned URLs work only on the S3 endpoint
(`<ACCOUNT_ID>.r2.cloudflarestorage.com`), not on a custom domain. GET, HEAD, PUT and DELETE can be presigned.

Without the keys the request answers `501` and `presignUrl()` resolves to `null`.

## Which one to use

The gateway needs no keys anywhere and no signing, so it is the default here, and it is what we ran on Cloudflare.
Direct transfer is what the prototype settled on for long videos, because bytes through a Worker were its slowest
part. Run it on your account before you rely on it, and tell us what you measured.
